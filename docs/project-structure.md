# Project Structure

This document explains the purpose of every major directory in the RouteUI repository.

The project follows a **pnpm workspace monorepo** architecture so multiple packages can be developed, tested, and released independently while sharing a common codebase.

# Root Directory

The repository root contains the shared configuration for the entire monorepo.

## package.json

Defines:

- Workspace scripts
- Development dependencies
- Project metadata

Current workspace commands include:

```bash
pnpm build
pnpm test
pnpm test:watch
pnpm test:coverage
pnpm format
```

---

## pnpm-workspace.yaml

Defines every workspace package.

Example:

```yaml
packages:
  - packages/*
  - examples/*
```

This allows pnpm to treat every package as part of one workspace.

---

## tsconfig.json

Shared TypeScript configuration used by every package.

Having one root configuration ensures consistent compiler behavior across the repository.

---

# packages/

This directory contains the publishable packages.

Current structure:

```text
packages/
└── core/
```

Future structure:

```text
packages/
├── core/
├── ui/
├── openapi/
├── cli/
├── fastify/
└── hono/
```

Each package has a single responsibility.

---

# packages/core

The core package contains the runtime scanning engine.

Everything required to discover routes lives here.

```text
core/
│
├── src/
├── tests/
├── dist/
├── package.json
└── tsup.config.ts
```

---

# src/

Contains the TypeScript source code.

```text
src/
├── adapters/
├── models/
├── types/
├── utils/
└── index.ts
```

---

## adapters/

Framework-specific integrations.

Current:

```text
adapters/
└── express.ts
```

Responsibilities:

- Read Express internals
- Extract routing information
- Convert Express objects into RouteUI models

The adapter isolates framework-specific code from the scanner.

Future:

```text
adapters/
├── express.ts
├── fastify.ts
└── hono.ts
```

---

## models/

Contains RouteUI's internal data models.

Example:

```text
models/
└── route.ts
```

Current model:

```ts
interface InternalRoute {
  method: HttpMethod;
  path: string;
}
```

These models are framework-independent.

---

## types/

Shared TypeScript definitions.

Examples:

- Express internal types
- HTTP method types
- Shared interfaces

These improve type safety while avoiding duplicated definitions.

---

## utils/

Shared helper functions.

Current utilities include:

- HTTP method normalization

Future utilities may include:

- Path normalization
- Route sorting
- Metadata extraction
- String utilities

---

## index.ts

The public entry point for the package.

It exports the APIs intended for consumers while hiding internal implementation details.

---

# tests/

Contains the unit tests for the core package.

Current tests verify:

- Single route detection
- Multiple route detection

Upcoming tests:

- Nested routers
- Route parameters
- Middleware detection
- Edge cases

The project uses **Vitest** for testing.

---

# dist/

Generated build output.

Contains:

- ESM build
- CommonJS build
- Type declarations

This directory is automatically generated by **tsup** and should never be edited manually.

---

# examples/

examples/

# Design Philosophy

The repository is organized around clear responsibilities.

```text
Source Code
        │
        ▼
Framework Adapter
        │
        ▼
Runtime Scanner
        │
        ▼
Internal Models
        │
        ▼
Future UI / Exporters
```

Each layer has a single responsibility.

This separation makes RouteUI easier to maintain, extend, and test.

---

# Future Growth

The repository structure is intentionally designed to scale.

As RouteUI grows, new packages can be added without affecting the existing architecture.

Examples include:

- Interactive UI
- CLI
- OpenAPI exporter
- Fastify adapter
- Hono adapter

The monorepo architecture allows all packages to evolve together while sharing tooling and configuration.

---

# Summary

The RouteUI repository follows four guiding principles:

- **Modularity** — every package has a clear responsibility.
- **Scalability** — new packages can be added without restructuring the project.
- **Maintainability** — framework-specific code is isolated from the core scanner.
- **Consistency** — shared tooling and configuration across the entire workspace.
